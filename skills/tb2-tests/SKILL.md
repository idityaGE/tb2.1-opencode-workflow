# TB2 Tests

Use when writing `tests/` for Terminal-Bench tasks.

Requirements:
- Read `.opencode/docs/local/workflow-profile.md` for create-versus-revision and validation policy.
- `.opencode/templates/tests/test.sh` is the only positive runner template. `tb2_create_task.sh` installs it for every new regular/UI task; restore that file from the template instead of composing a competing body from prose or copied docs.
- `tests/test.sh` must run Python pytest, normally `python -m pytest --ctrf /logs/verifier/ctrf.json /tests/test_outputs.py -rA`, and always write `/logs/verifier/reward.txt`. Use Python pytest tests to drive Java, JavaScript, Go, browser, or other systems instead of replacing pytest with their native test runners.
- Do not add runtime installers, native test runners, `set -e`, commands between pytest and status capture, or trailing commands after the template's reward block. Structural lint enforces the mechanical runner contract.
- `tests/test_outputs.py` should use behavioral assertions, not implementation details.
- Every test function should have a docstring.
- Cover every explicit prompt requirement, every normative clause used from an approved agent-visible `README.md`, `spec.md`, or `rule.md` under `environment/`, fair unavoidable implicit behavior, and important edge case. If multiple reasonable outcomes exist, document the chosen observable behavior before testing it rather than treating it as implicit.
- If tests check an output file, schema, protocol, or rule detail, ground it fairly in the prompt or an explicitly referenced public document. Detailed contract text may live in that document only when `instruction.md` already introduces the governed requirement category.
- Before validation, run a private bidirectional requirement-to-test audit. Atomize independently violable obligations as `R1`, `R2`, and so on, and record each obligation's source, covering pytest functions, the assertion or independent-reference result that rejects a violation, input class, and one plausible violation probe. Execution alone, a broad end-to-end test, or file existence does not prove coverage unless the mapped assertion distinguishes compliant from non-compliant behavior.
- Atomize every independently falsifiable member of an `and`/`or` list, every named enum/status/reason, every observable conditional branch, every boundary or mode, every schema exactness rule, and every ordering key or tie-break. One representative case does not cover distinct public alternatives; merge rows only with a private equivalence rationale showing how the same assertion rejects each alternative.
- Reverse-audit every semantically distinct verifier assertion to an explicit instruction requirement, approved contract clause, or truly unavoidable implicit behavior. If no basis exists, add the smallest neutral observable contract or remove the unfair assertion. A test is not grounded merely because it catches a seeded bug.
- For assertions over raw bytes, full strings, stdout/stderr, exit codes, exact key sets, named values, or output order, cite the public clause that makes that exactness observable. Prefer semantic comparisons when exact representation is not intentionally public; when order is public, use mixed data that distinguishes every documented ordering key instead of sets, dictionaries, or a single-key example.
- Extend that matrix into a private four-way contract alignment audit with columns for the exact public clause, oracle behavior that satisfies it, verifier assertion that rejects its violation, and NOP/negative-probe evidence. Include all requirements from `instruction.md` and every explicitly referenced README/spec/rule file. The audit passes only with zero oracle omissions, zero uncovered requirements, zero ungrounded verifier behaviors, meaningful NOP failure, coverage of every critical edge class, and verifier relevance for every intended hidden defect or failure layer. Re-run the complete audit after any instruction, approved contract, verifier, oracle, or runtime-baseline change; never limit a repair audit to the reviewer's examples or coarsen unchanged rows to claim closure. After the final edit, check every new or changed public clause for a new oracle/verifier obligation and every new or changed assertion for public grounding, then finish all neighboring rows in the affected requirement family before reporting readiness. Keep the matrix private; do not upload it or leak requirement IDs through task files, test names, fixtures, or comments.
- Criterion 38 repair mode: if reviewer output reports `38 [HIGH] FAIL`, rebuild the complete requirement-to-test matrix instead of patching the cited example. For every uncovered requirement row, either add a public-grounded behavioral assertion that rejects a plausible violation and is satisfied by the oracle, or narrow/remove that public requirement when it was not intended as a graded obligation. Cover sibling enum values, branches, boundaries, ordering keys, and tie-breaks in the same family before returning. Use parameterized tests to keep the suite compact only when each row still has a distinct assertion/probe in the private matrix.
- Verifiers must establish real correctness, not only file existence, formatting, schema shape, status codes, or other high-level structure. Recompute results with independent logic or check load-bearing semantic invariants and cross-artifact consistency.
- Test behavior by running the task entrypoint and checking results. Do not grep, parse, or otherwise inspect implementation source to require a function name, library, syntax pattern, algorithm, or code fragment.
- Reject vacuous assertions and loops that perform no checks. For every semantic assertion group, demonstrate at least one plausible violating result or mutant that the mapped assertion rejects; never accept always-true checks or tests whose result is independent of task output.
- Preserve difficulty with behavioral depth rather than hidden requirements. Use multiple same-schema cases, including larger, cyclic, reordered, malformed, or deterministically generated inputs when the public contract permits them; check semantic invariants instead of relying only on exact visible outputs.
- Give every intended hidden defect or failure layer an independent behavioral rejection path in the verifier as well as integrated coverage. Explicitly reject no-op, hardcoded, partial, and visible-fixture-only solutions without inspecting forbidden implementation details.
- Do not encode solution hints or inspect forbidden implementation details.
- Tests must be deterministic. Do not make pass/fail depend on timing, hardware, unordered iteration, one particular random draw or seed value, or ambient host state. With `allow_internet = false`, tests must not fetch dependencies or data; with `true`, network use must be limited to the task's genuine need and grading must remain stable.
- Preserve anti-cheating boundaries: never bake `tests/` or `solution/` into the agent-visible image; independently recompute data-file results instead of trusting an editable final value; and pin any permitted `git clone` or checkout to a specific immutable commit so newer answers are unreachable.
- Treat NOP as an alignment check, not only a reward check. The untouched task must earn 0 because required behavior is absent, not because the verifier crashed, dependencies are missing, paths are wrong, or the environment is unusable. Inspect the NOP failure and repair infrastructure-caused failures before accepting it.
- `tests/test.sh` must not install packages at runtime. Bake pytest, pytest-json-ctrf, plugins, browser drivers, wheels, npm packages, and other verifier dependencies into the Docker image. Local-only installs from preloaded wheels, such as `pip install --no-index -f /opt/wheels pytest==8.4.1`, are acceptable when needed.
- The same verifier must score oracle and agent runs.
- Do not use latency or performance thresholds as pass/fail criteria.
- Do not branch test behavior on oracle-vs-agent mode.
